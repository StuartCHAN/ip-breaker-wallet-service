# Sprint 1: Deposit address management

## Scope

- list active, deposit-enabled Sepolia assets;
- allocate one deposit address per user and network from a pre-provisioned pool;
- return an existing assignment for repeated or concurrent requests;
- keep private keys and signing material outside the wallet database;
- normalize stored Ethereum addresses to lowercase and display EIP-55 checksum addresses;
- define `AddressProvider` and `Signer` ports for later KMS, HSM, TEE, or MPC adapters.

## API

```http
GET /api/v1/assets

POST /api/v1/users/{userId}/deposit-addresses
Content-Type: application/json

{"networkCode":"SEPOLIA"}

GET /api/v1/users/{userId}/deposit-addresses?networkCode=SEPOLIA
```

Allocation is idempotent for `(network, user, address type)`. The allocator uses a short
database transaction and `SELECT ... FOR UPDATE SKIP LOCKED`; database unique constraints
remain the final concurrency boundary.

## Address provisioning boundary

`wallet_address` contains public addresses and an optional derivation index only. It must
never contain a mnemonic, seed, private key, or decrypted signing material. Operations must
provision `AVAILABLE` addresses generated by an external custody component before enabling
allocation. The application returns `503 WALLET-503-001` when the pool is empty.

Example development-only provisioning statement:

```sql
INSERT INTO wallet_address
    (network_id, address, derivation_index, address_type, status)
SELECT id, LOWER('0x1111111111111111111111111111111111111111'), 1, 'DEPOSIT', 'AVAILABLE'
FROM chain_network WHERE network_code = 'SEPOLIA';
```

Do not use the example address for real funds.

## Acceptance checks

- `./mvnw -B -ntp verify` passes on Java 21;
- Flyway applies V1 through V3 to MySQL 8;
- repeated allocation for one user returns the same address;
- concurrent allocation does not bind multiple addresses to one user;
- separate users can lock separate pool rows without blocking each other;
- an exhausted pool returns a stable service-unavailable error;
- no private-key field or secret appears in the schema, API, logs, or repository.
